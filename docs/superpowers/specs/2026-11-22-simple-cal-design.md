# simple-cal 설계 문서

작성일: 2026-11-22
상태: 승인됨 (2026-11-22)

## 1. 무엇을, 왜

혼자 쓰는 개인용 일정 관리 웹앱. 핵심은 **캘린더를 여러 개 두고, 캘린더마다 일정(event)과 할 일(task)을 함께 담아 나눠 관리하는 것**이다.

구글 캘린더는 할 일을 캘린더가 아닌 별도의 "할 일 목록"에 두기 때문에 "회사" 캘린더에 회사 일정과 회사 할 일을 같이 둘 수 없다. simple-cal은 캘린더가 일정과 할 일을 모두 소유한다는 점이 차별점이다.

이번 작업은 **프론트엔드만** 만든다. 백엔드는 사용자가 이후 스프링부트로 직접 만든다. 그 전까지는 브라우저 안의 가짜 API(MSW)로 동작한다.

## 2. 목표 / 비목표 / 안티목표

**목표**
- 캘린더 여러 개를 만들고(이름·색 직접 지정), 켜고 끌 수 있다.
- 일정과 할 일을 한 화면에 섞어서 본다.
- 주간 보기를 기본으로, 월간·목록 보기로 전환한다.
- 빈 칸 클릭으로 바로 새 항목을 만든다.
- 나중에 스프링부트 백엔드를 붙일 때 화면 코드를 거의 고치지 않는다.
- 백엔드가 구현해야 할 REST API 계약을 이 문서에서 정의한다.

**비목표 (첫 버전에서 제외)**
- 연간 보기, 사용자 지정 기간(예: 4일) 보기
- 로그인·여러 사용자·공유 (백엔드 단계에서 다룸)
- 반복 일정, 알림, 외부 캘린더(구글 등) 가져오기/동기화
- 오프라인 동기화, 모바일 앱

**안티목표 (이렇게 되면 실패)**
- 일정과 할 일이 결국 따로 노는 화면이 되는 것 — 둘은 같은 주간 격자 안에 섞여 보여야 한다.
- 할 일이 캘린더와 무관한 별도 목록에 속하는 구조 — 할 일은 반드시 하나의 캘린더에 속한다.
- 백엔드 연결 시 데이터 접근 코드를 갈아엎어야 하는 구조.

## 3. 결정된 사항

### 3.0 폴더 구성 (사용자 결정)
```
simple-cal/
├── frontend/   ← 이번 작업 (React + Vite 프로젝트)
├── backend/    ← 나중에 사용자가 스프링부트로 직접 (이번엔 만들지 않음)
└── docs/       ← 프론트·백엔드 공통 설계 문서
```

### 3.1 기술 스택
- React + TypeScript + Vite
- 달력 화면: FullCalendar (`@fullcalendar/react`, daygrid / timegrid / list / interaction 플러그인)
- 가짜 API: MSW(Mock Service Worker). 화면 코드는 처음부터 `fetch('/api/...')`로 실제 서버처럼 호출하고, MSW 핸들러가 응답한다. MSW 핸들러는 데이터를 `localStorage`에 저장해 새로고침 후에도 유지한다.
- (사용자 결정) 백엔드 전까지는 만들면서 확인하는 용도로만 쓴다. MSW는 개발 모드(`pnpm dev`)에서만 켜고, 프로덕션 빌드에는 넣지 않는다. 브라우저 저장소의 데이터를 백엔드로 옮기는 기능은 만들지 않는다.
- 백엔드 연결 시: MSW를 끄고 `/api`를 스프링부트 서버로 프록시(Vite dev proxy)하면 된다.

### 3.2 데이터 모델

**Calendar**
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string | |
| name | string | 사용자가 지정 |
| color | string | `#RRGGBB`, 사용자가 지정 |
| visible | boolean | 사이드바 체크 상태 (서버에 저장 — 다른 기기에서도 유지) |

**Item** — 일정과 할 일을 하나의 타입으로 다루고 `type`으로 구분한다.
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string | |
| calendarId | string | 반드시 하나의 캘린더에 속함 |
| type | `"event"` \| `"task"` | |
| title | string | |
| memo | string? | |
| date | `YYYY-MM-DD` | 시작 날짜. 일정·할 일 모두 **필수** |
| startTime | `HH:mm`? | 없으면 하루 종일 |
| endDate | `YYYY-MM-DD`? | 일정만. 여러 날 일정용. 없으면 date와 같음 |
| endTime | `HH:mm`? | 일정만. startTime이 있으면 필수 |
| done | boolean | 할 일만 |

- 할 일은 날짜가 꼭 있고 시간은 선택. 시간이 있는 할 일은 그 시각에 짧은 블록(30분 높이)으로 표시하고 끝 시간은 없다.
- (내 판단) 하나의 Item 타입을 쓴다. 해당 타입에 쓰지 않는 필드는 항상 `null`로 보낸다(일정의 `done`은 `false`).
- (내 판단) 편집 창에서 일정↔할 일 전환을 허용한다. 일정→할 일: `endDate`/`endTime`을 비우고 `done=false`. 할 일→일정: 시간이 있으면 `endTime`=시작+1시간, 없으면 하루 종일 일정.
- (내 판단) 날짜 범위는 모두 **포함(inclusive)**: `endDate`는 마지막 날 자체. FullCalendar의 배타적 끝 날짜와의 변환은 화면 쪽 어댑터 한 곳에서만 한다.
- 시간대(timezone): 개인용이므로 모든 날짜·시간은 사용자의 로컬 시간 기준 "벽시계 시각"으로 저장하고 변환하지 않는다.

### 3.3 화면

```
┌──────────────┬──────────────────────────────────────────────┐
│ 내 캘린더  ＋ │  < 이번 주 >  2026년 11월 23–29일   [주][월][목록] │
│ ☑ ■ 회사     ├──────────┬──────────┬──────────┬─────────────┤
│ ☑ ■ 개인     │  월 23   │  화 24   │  수 25   │ ...         │
│ ☑ ■ 운동     ├──────────┼──────────┼──────────┤ (하루 종일 줄)│
│              │☐ 보고서  │☑ 반품    │☐ 단백질  │             │
│              ├──────────┼──────────┼──────────┤ (시간 격자) │
│              │10 주간회의│12 점심   │14 1:1    │             │
│              │19 헬스   │          │19 헬스   │             │
└──────────────┴──────────┴──────────┴──────────┴─────────────┘
```

- **왼쪽 사이드바**: 캘린더 목록. 체크박스로 표시/숨김, 색 표시. `＋`로 캘린더 추가, 캘린더 이름 옆 메뉴로 이름·색 수정과 삭제.
- **기본 화면은 주간 보기.** 요일마다 맨 위 "하루 종일" 줄에 시간 없는 할 일(과 하루 종일 일정), 아래 시간 격자에 시간 있는 일정·할 일.
- 상단에서 이전/다음/오늘 이동, 주간·월간·목록 보기 전환.
- **일정**은 캘린더 색으로 채운 막대. **할 일**은 체크박스 + 제목, 캘린더 색은 왼쪽 테두리로. 체크박스 클릭 시 바로 완료 토글.
- **완료한 할 일**은 사라지지 않고 줄이 그어진 채 회색으로 남는다.
- **밀린 할 일 (사용자 결정: 오늘로 따라오기)**: 날짜가 오늘 이전이고 완료되지 않은 할 일은 원래 날짜 칸이 아니라 **오늘의 하루 종일 줄**에 "밀림" 표시와 원래 날짜(예: `11/20부터`)를 붙여 보여준다. 원래 날짜 칸에는 표시하지 않는다. 저장된 `date`는 바꾸지 않는다. 완료하면 원래 날짜 칸으로 돌아가 완료 상태로 보이고, 다른 날로 끌어 옮기면 `date`가 그날로 바뀐다. 목록 보기에서는 오늘 맨 위에 모아 보여준다. 오늘이 화면에 없는 주·달을 볼 때는 보이지 않는다.
- **새 항목 만들기**: 빈 시간 칸 또는 하루 종일 줄을 클릭하면 그 자리에 작은 입력 창이 뜬다. 창에서 제목, 일정/할 일 선택, 캘린더 선택. 시간 칸에서 만들면 그 시각이 채워지고(일정은 기본 1시간), 하루 종일 줄에서 만들면 시간 없이 만들어진다. "자세히"를 누르면 아래 편집 창으로 넘어간다.
- **항목 클릭**: 편집 창(모달)에서 모든 필드 수정, 삭제.
- **드래그**: 일정과 시간 있는 할 일은 끌어서 날짜/시간을 옮기고, 일정은 아래쪽 끝을 끌어 길이를 바꾼다. 하루 종일 항목도 다른 날로 끌어 옮길 수 있다.
- (내 판단) 하루 종일 줄 ↔ 시간 격자 사이 드래그 허용. 시간 격자 → 하루 종일 줄: 시간(`startTime`/`endTime`)을 지운다. 하루 종일 줄 → 시간 격자: 놓은 시각이 `startTime`, 일정이면 `endTime`=+1시간.

### 3.4 REST API 계약 (MSW가 흉내내고, 스프링부트가 나중에 구현)

JSON, 필드명 camelCase, 위 데이터 모델 그대로.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/calendars` | 캘린더 전체 |
| POST | `/api/calendars` | 생성 (`name`, `color`) → 생성된 Calendar |
| PATCH | `/api/calendars/{id}` | 부분 수정 (`name`, `color`, `visible`) |
| DELETE | `/api/calendars/{id}` | 삭제. 소속 항목도 함께 삭제 |
| GET | `/api/items?from=YYYY-MM-DD&to=YYYY-MM-DD` | 기간과 겹치는 항목 (모든 캘린더, 숨긴 것 포함; 걸러내기는 화면에서) |
| GET | `/api/items/overdue?today=YYYY-MM-DD` | `type=task`, `done=false`, `date < today`인 항목 전체. "오늘"은 클라이언트가 자기 로컬 날짜로 보낸다 |
| POST | `/api/items` | 생성 → 생성된 Item |
| PATCH | `/api/items/{id}` | 부분 수정 (완료 토글, 드래그 이동 포함) |
| DELETE | `/api/items/{id}` | 삭제 |

- (내 판단) `GET /api/items`의 `from`, `to`는 둘 다 포함. "겹친다"는 `date <= to` 그리고 `(endDate ?? date) >= from` — 기간 이전에 시작한 여러 날 일정도 포함.
- (내 판단) PATCH 규칙: 빠진 필드는 그대로 두고, `null`을 보낸 필드는 비운다. 스프링부트에서는 `Map` 또는 `JsonNullable`로 둘을 구분해야 한다.
- 오류: 4xx/5xx와 RFC 9457 Problem Details(`application/problem+json`; `type`, `title`, `status`, `detail`, `instance`). 한국어 문구는 `detail`. 상태 코드 기준과 `type` 목록은 [백엔드 설계서 3.4](2026-11-22-simple-cal-backend-design.md). 화면은 실패 시 `detail`을 알림으로 띄우고 변경을 되돌린다. (2026-11-22 변경 — 처음엔 `{ "message": string }`였음, 사용자 결정)
- `id`는 서버(MSW)가 만든다.

## 4. 검토한 방식

1. **FullCalendar + MSW 가짜 API** — 선택. 달력의 어려운 부분(주/월/목록, 겹침 배치, 드래그)은 검증된 라이브러리에 맡기고, 화면 코드는 처음부터 실제 API를 호출하므로 백엔드 연결 시 MSW만 끄면 된다. API 계약도 미리 써보며 검증된다. 대가: 달력 모양과 동작이 라이브러리 방식에 어느 정도 묶인다.
2. FullCalendar + localStorage 직접 사용 — 가장 빨리 시작하지만, 백엔드 연결 시 데이터 접근 코드를 다시 짜야 하고 API 모양이 그때야 정해진다.
3. 달력 직접 구현 + MSW — 모양을 완전히 통제할 수 있지만 작업량이 몇 배이고 겹침·날짜 경계 버그를 직접 잡아야 한다.
